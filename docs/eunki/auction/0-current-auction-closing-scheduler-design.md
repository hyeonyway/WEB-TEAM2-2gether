# 기존 경매 마감 스케줄러 설계

## 목적

이 문서는 데드락 예방 개선을 적용하기 전 경매 마감 스케줄러의 구조와 처리 방식을 기록한다. [데드락 예방 설계](2-auction-scheduler-deadlock-prevention-design.md)와 비교해 트랜잭션 범위, 락 점유 범위, 실패 격리 방식이 어떻게 달라졌는지 확인하는 기준선이다.

## 구성 요소

| 구성 요소 | 역할 | 실행 방식 |
| --- | --- | --- |
| `AuctionDeadlineScheduler` | 가장 가까운 마감 시각에 정시 마감 작업을 예약 | 경매 생성·연장 후 재예약하는 단일 원샷 타이머 |
| `AuctionClosingScheduler` | 정시 작업 누락, 서버 재시작 등을 보완 | 고정 주기 백업 작업 |
| `AuctionCommandService.closeDueAuctions` | 마감 후보 조회와 실제 종료·정산을 한 번에 수행 | 최대 100건을 하나의 트랜잭션에서 처리 |
| `WalletService.capture` | 낙찰자의 예치금을 포인트로 확정 | 마감 트랜잭션 안에서 낙찰자 지갑을 비관적으로 잠금 |

## 기존 실행 흐름

```text
AuctionDeadlineScheduler ─┐
                           ├─ closeDueAuctions(now, 100)
AuctionClosingScheduler ──┘
                           │
                           ▼
              단일 트랜잭션 시작
                           │
                           ▼
 SELECT auctions ... WHERE close_time <= now
 ORDER BY close_time, id
 FOR UPDATE LIMIT 100
                           │
                           ▼
      잠긴 경매를 순차적으로 종료
        ├─ 최고 입찰 조회
        ├─ 경매 상태를 ENDED 또는 FAILED로 변경
        ├─ 낙찰자 wallet 행 잠금 및 capture
        └─ 종료 이벤트 발행
                           │
                           ▼
              단일 트랜잭션 커밋
```

## 락과 트랜잭션 특성

### 넓은 경매 락 범위

마감 후보 조회가 `SELECT ... FOR UPDATE`이므로 조회된 최대 100개의 경매 행은 첫 번째 경매의 정산부터 마지막 경매의 정산까지 모두 잠긴다. 하나의 경매 처리에 지갑·예치금 정산이 지연되면, 같은 배치에 포함된 나머지 경매의 입찰도 함께 대기할 수 있다.

### 배치 전체 롤백

한 경매의 지갑 정산이나 이벤트 처리에서 예외가 발생하면 같은 트랜잭션의 다른 마감 결과도 함께 롤백된다. 다음 백업 주기에 다시 시도되지만, 이미 처리에 성공했던 경매까지 재처리 대상이 된다.

### 중복 실행 가능성

정시 마감 스케줄러와 백업 스케줄러가 겹치면 같은 마감 후보를 조회할 수 있다. 비관적 락이 최종적으로 한 작업만 진행시키지만, 다른 작업은 넓은 배치 락이 해제될 때까지 대기한다.

### 다중 지갑 락 규칙

마감 자체는 낙찰자 지갑 한 건만 확정한다. 반면 입찰은 새 입찰자의 예치와 기존 최고 입찰자의 예치 해제를 함께 수행할 수 있다. 이때 서로 다른 경매의 교차 입찰이 발생해도 지갑 락 순서를 통일하지 않으면 지갑 간 순환 대기가 생길 수 있다.

## 개선안과의 비교

| 항목 | 기존 설계 | 개선 설계 |
| --- | --- | --- |
| 후보 조회 | 경매 엔티티 최대 100건을 `FOR UPDATE`로 조회 | 락 없이 경매 ID만 조회 |
| 종료 트랜잭션 | 배치 전체가 하나의 트랜잭션 | 경매 한 건당 `REQUIRES_NEW` 트랜잭션 |
| 락 점유 | 배치의 모든 경매 락을 마지막 정산까지 보유 | 처리 중인 경매 한 건만 보유 |
| 실행 방식 | 순차 처리 | 제한된 실행기에서 병렬 처리 |
| 실패 영향 | 한 건 실패 시 배치 전체 롤백 | 실패·재시도 범위를 해당 경매로 한정 |
| 백업 주기 | 10초 기본값 | 60초 기본값 |
| 지갑 락 | 다중 지갑 순서가 코드 흐름에 의존 | 사용자 ID 오름차순을 명시적 불변조건으로 유지 |
