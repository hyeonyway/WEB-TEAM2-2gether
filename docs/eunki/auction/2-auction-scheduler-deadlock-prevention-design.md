# 경매 마감 스케줄러 데드락 예방 설계

## 개요

경매 정시 마감 스케줄러와 백업 스케줄러는 같은 마감 대상을 동시에 처리할 수 있다. 기존 구현은 최대 100개의 `auctions` 행을 `SELECT ... FOR UPDATE`로 먼저 잠근 뒤, 각 낙찰자의 `wallets` 행과 예치금 행을 정산했다. 이 긴 트랜잭션 범위는 마감 직전 입찰의 경매·지갑 락과 교차해 데드락 및 긴 대기를 만들 수 있다. 기존 구조의 상세는 [기존 경매 마감 스케줄러 설계](0-current-auction-closing-scheduler-design.md)를 참고한다. 백업 스케줄러는 정시 마감의 안전망이므로 기본 주기를 60초로 둔다.

이 설계의 핵심은 다음 두 가지다.

1. 마감 후보를 읽을 때는 락을 잡지 않고 ID만 조회한다.
2. 한 트랜잭션에서 둘 이상의 지갑을 처리해야 하면 항상 사용자 ID 오름차순으로 지갑 락을 얻는다.

## 검토한 대안

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 기존 배치 `FOR UPDATE` 유지 | 구현이 단순하다. | 최대 100개 경매 락과 범위 락을 오래 점유해 입찰 지연과 데드락 위험이 크다. |
| 스케줄러를 하나로 통합 | 동일 인스턴스의 중복 실행을 줄인다. | 다중 인스턴스와 입찰 요청 간의 락 순서 문제를 해결하지 못한다. |
| 무락 ID 조회 + 단건 트랜잭션 순차 처리 | 락 범위와 실패 범위를 줄인다. | 다수의 동시 마감에서 처리 지연이 커질 수 있다. |
| **무락 ID 조회 + 제한 병렬 단건 트랜잭션** | 락 범위와 점유 시간을 최소화하면서 처리량을 유지한다. 중복 후보도 행 잠금 후 재검증으로 안전하게 무시한다. | 실행기 크기와 재시도 횟수를 제한해야 DB 연결 풀을 압박하지 않는다. |

네 번째 방식을 채택한다.

## 처리 흐름

```text
두 스케줄러
    │
    ▼
락 없는 후보 ID 조회 (close_time, id 순 / limit 100)
    │
    ▼
최대 4개 작업으로 제한 병렬 처리
    │
    ▼
각 ID마다 새 트랜잭션
  1. auction 한 건 FOR UPDATE
  2. OPEN/ENDING 및 close_time <= 기준 시각 재검증
  3. 최고 입찰 확정, 낙찰자 wallet 한 건 capture
  4. 커밋
```

후보 ID 조회는 스냅샷일 뿐이다. 다른 스케줄러나 즉시 구매가 먼저 경매를 종료했으면, 단건 트랜잭션의 재검증 결과는 빈 결과가 되며 별도 오류 없이 끝난다.

## 락 순서 규칙

### 경매 마감

마감 트랜잭션은 대상 경매 한 건을 잠근 뒤 낙찰자 지갑 한 건만 `capture`한다. 따라서 마감 경로 자체에는 두 지갑 간 순서 문제가 없다. 기존처럼 여러 경매를 한 트랜잭션에 묶지 않으므로 다른 경매의 락도 보유하지 않는다.

### 입찰과 기존 최고 입찰자 교체

입찰은 현재 입찰자 예치(`hold`)와 기존 최고 입찰자 예치 해제(`release`)를 모두 수행할 수 있다. 두 지갑을 잠글 때는 **항상 작은 사용자 ID를 먼저** 처리한다.

- 기존 최고 입찰자 ID가 더 작으면 `release → hold`
- 새 입찰자 ID가 더 작으면 `hold → release`

이 규칙은 모든 입찰 경로에서 동일하게 적용해야 하며, 순서 회귀 테스트로 고정한다. 지갑 락 순서 통일은 서로 다른 경매를 동시에 입찰하는 경우의 지갑 간 순환 대기를 막는 핵심 불변조건이다.

## 실패 및 재시도

- 비관적 락 획득 실패/데드락은 해당 경매 단건 트랜잭션만 최대 3회 재시도한다.
- 최종 실패 또는 업무 예외는 해당 경매만 로그로 남기고 다음 후보 처리를 계속한다. 백업 스케줄러가 다음 주기에 다시 후보로 수집한다.
- 병렬 실행기는 4개 작업으로 제한하고, 대기열은 100개로 제한한다. 병렬도는 DB 커넥션 풀과 실제 마감 처리 시간을 관찰해 조정한다.
- 백업 스케줄러의 기본 주기는 60초이며, 정시 마감 누락 시 최대 60초의 추가 지연을 허용하는 대신 중복 후보 조회와 락 경합을 줄인다.

## 검증 기준

- 후보 조회 쿼리는 `FOR UPDATE` 없이 `id`만 반환한다.
- 각 후보는 독립 `REQUIRES_NEW` 트랜잭션에서 해당 `auction` 행만 잠근 뒤 종료 조건을 다시 확인한다.
- 같은 후보가 두 스케줄러에 중복 수집되어도 한 번만 종료·정산된다.
- 이전 최고 입찰자와 새 입찰자가 다른 경우, 지갑 서비스 호출 순서는 사용자 ID 오름차순이다.
- 한 후보의 락 충돌/업무 실패가 같은 배치의 다른 후보를 롤백하지 않는다.
