# SSE 아키텍처 개요

**배경:** 경매 상세와 대시보드/랭킹은 여러 유저가 동시에 보는 화면이라 폴링만으론 체감 지연이 크다. 특히 경매 상세는 "방금 남이 입찰함"을 즉시 보여주지 못하면 3분 연장(스나이핑 방지) 정책의 체감 효과가 떨어진다. 이 문서는 실시간 전달 방식으로 검토한 기술과 각 지점에서 대안 대비 선택 이유를 기록한다.

## 1. 실시간 전달 방식 — SSE

| 후보 | 채택 | 이유 |
|---|---|---|
| 폴링(기존안) | 미채택 | 경매는 1초 단위로 의미가 갈리는데 폴링으로는 실시간성이 부족하다. HTTP request connection을 맺고 끊는 것 자체의 부하도 크다 |
| WebSocket | 미채택 | 양방향 통신을 지원하는데 우리 서비스 특성상 더 많은 자원을 쓰면서 양방향 통신을 할 이유가 없다(입찰 자체는 기존 POST). `spring-websocket`/STOMP 등 추가 의존성 필요 |
| SSE | 채택 | Spring 내장 `SseEmitter`로 추가 의존성 없음. 브라우저 `EventSource`가 재연결(`Last-Event-ID`)을 기본 지원. 기존 HTTP 인프라(ALB/Nginx) 그대로 통과 |

**목록 페이지 구독 전략(팀 회의 결론):** 스크롤+페이지네이션을 고려했으나, 스크롤할 때마다 프론트엔드가 화면에 표시되는 경매를 확인해 그것만 재구독하는 구현이 쉽지 않다. 개발 편의를 위해 대시보드와 경매 목록 모두 auctionId 필터링 없이 **전체 연결**로 구현한다. 시간이 되거나 트래픽 문제가 실제로 발생하면 그때 보이는 항목만 구독하는 방식으로 개선한다.

## 2. 인스턴스 간 이벤트 릴레이 — Redis Pub/Sub 미채택(확정)

여러 앱 인스턴스가 떠 있으면 이벤트를 처리한 인스턴스와 클라이언트의 SSE 연결을 물고 있는 인스턴스가 다를 수 있어 릴레이가 필요해지는데, 검토 결과는 다음과 같다.

| 후보 | 채택 | 이유 |
|---|---|---|
| Kafka/RabbitMQ | 미채택 | 신규 인프라 도입 비용 — 이 프로젝트 규모엔 오버스펙 |
| Redis Streams | 미채택 | SSE push는 화면 갱신 트리거일 뿐 진짜 상태는 DB(auctions/bids)에 있다. 메시지 유실이 데이터 유실로 이어지지 않으므로 Streams의 영속성/consumer group은 불필요한 복잡도 |
| Redis Pub/Sub | **미채택(팀 회의 확정)** | 현재 단일 인스턴스 환경이라 인스턴스 간 릴레이 자체가 필요 없다. 이벤트 처리하는 곳과 SSE 연결을 들고 있는 곳이 항상 같은 프로세스이므로 순수 인메모리 `@EventListener` → 로컬 `SseEmitter` push만으로 충분하다 |

이 결정에 따라 **`global.realtime` 같은 별도 공용 릴레이 모듈은 만들지 않는다.** 정세호(경매/대시보드)와 임하민(알림)이 각자 패키지 안에서 로컬 emitter 레지스트리만 관리하면 된다. 멀티 인스턴스로 스케일아웃할 때만 `RealtimePublisher.publish(...)` 호출을 추가하면 되고, 로컬 emitter 관리 로직은 바뀌지 않는다.

**채널 네이밍(초안, 팀 합의 전):** `auction:{auctionId}:updates`, `dashboard:insights:updates`, `user:{userId}:auctions:updates`, `user:{userId}:notifications:updates`

## 3. SSE 인증 범위 — 공개 데이터는 무인증, 개인화 데이터만 티켓

브라우저 `EventSource`는 커스텀 헤더(`Authorization`)를 지정할 수 없다(API 스펙 자체의 제약이며 프로토콜 문제가 아니다). 대안 비교:

| 후보 | 채택 | 이유 |
|---|---|---|
| JWT를 쿼리파라미터에 그대로 | 미채택 | 서버/프록시 access log, 브라우저 히스토리, Referer 헤더로 실제 토큰이 유출됨 |
| 쿠키 기반 인증 | 미채택 | 기존 인증체계가 `Authorization` 헤더 기반 JWT라 SSE 하나 때문에 쿠키 세션을 별도 도입하면 인증 방식이 두 갈래로 갈라짐 |
| `fetch` + `ReadableStream`으로 직접 파싱, 진짜 JWT 헤더 사용 | 검토 후 기각(팀 회의 확정) | 백엔드 티켓 인프라는 없어도 되지만 재연결/이벤트 파싱을 프론트에서 직접 구현해야 한다. 통제하기 어려운 프론트 복잡성을 늘리기보다, 통제 가능한 백엔드 복잡성이 늘어나는 쪽이 문제 발생 시 더 유연하게 수정 가능하다고 판단해 최종 기각 |
| WebSocket으로 전환 | 검토 후 미채택 | 브라우저 네이티브 `WebSocket`도 커스텀 헤더 불가 — 동일한 문제가 그대로 남고, 불필요한 양방향 채널만 추가됨 |
| 1회용 짧은 TTL 티켓(채택) | 채택 | 기존 `Authorization` 헤더로 티켓 발급 요청 → 짧은 TTL의 1회용 랜덤값만 쿼리파라미터로 전달 → 연결 수립 후 즉시 폐기. 로그/히스토리에 남아도 이미 소모된 값이라 무해함 |

**추가로 확인한 것:** 경매 목록/상세의 현재가·입찰 데이터는 로그인 여부와 무관하게 동일한 공개 시세 데이터다. 따라서 이 두 스트림은 **인증 자체가 불필요**하며, 티켓이 필요한 건 개인화 데이터를 다루는 대시보드·알림 스트림뿐이다. 상세 구현은 A(김현문) 담당 문서 [../auth/5-current-user-and-sse-auth.md](../auth/5-current-user-and-sse-auth.md) 참고.

티켓 저장소도 현재 배포 구조와 동일하게 단일 인스턴스를 기준으로 한다.
`ConcurrentHashMap`에 사용자 ID와 30초 만료 시각을 저장하고, 검증 시
`remove()`로 원자적으로 소비한다. 사용되지 않고 만료된 티켓은 주기적으로
정리한다. 애플리케이션이 여러 인스턴스로 늘어나면 발급 인스턴스와 SSE 연결
인스턴스가 달라질 수 있으므로, 그 시점에만 `TicketProvider` 구현체를 공유
저장소 기반으로 교체한다.

## 4. 캐시 계층 — Redis(개인화) vs CDN(공개·정적) 역할 분리

| 데이터 성격 | 채택 계층 | 이유 |
|---|---|---|
| 개인화 데이터, 즉시 무효화 필요 | Redis(앱 캐시) | CDN에 개인화 응답을 잘못 캐싱하면 크로스유저 데이터 유출로 이어짐. Redis는 TTL/명시적 invalidate가 밀리초 단위 |
| 완전 공개·비개인화·정적(카드 이미지, 공개 랭킹 Top5, 시세차트) | CDN(CloudFront) | 유저 구분 없이 응답이 동일하므로 엣지 캐싱으로 오리진 부하 절감. 단, 무효화 전파가 느려 초단위 즉시성엔 부적합 |

## 5. 담당 배분 (팀 회의 결론)

| 영역 | 담당 | 비고 |
|---|---|---|
| 경매 목록/상세 SSE 처리(연결관리, emitter) | 정세호 | 이은기가 발행하는 이벤트를 구독 |
| 대시보드/랭킹 SSE 처리 | 정세호 | 원래 담당(캐싱+쿼리최적화)과 함께 |
| 알림 SSE 처리 | 임하민 | 원래 담당(알림 저장/조회)과 함께 |
| 이벤트 생성(발행) | 이은기 | `AuctionCreatedEvent`/`BidPlacedEvent`/`AuctionClosedEvent` 발행만 담당. 상회 입찰 정보는 `BidPlacedEvent.previousBidderId`에 포함하며 SSE emitter/연결관리는 직접 만들지 않는다 |
| SSE 티켓 발급/검증 | 김현문 | 기존 JWT/`CurrentUserProvider` 소유 연장선. 상세는 [../auth/5-current-user-and-sse-auth.md](../auth/5-current-user-and-sse-auth.md) |

2절 결정(Redis Pub/Sub 미채택)에 따라 별도 `global.realtime` 공용 모듈이 필요 없어졌다 — 정세호/임하민이 각자 담당 영역 안에서 로컬 emitter만 관리하면 된다.

## 6. 확장 시나리오 — 핫경매 대응(현재 미채택)

경매 하나에 트래픽이 몰려 DB 락 대기가 실제 병목이 되는 경우를 대비한 후보안. **부하테스트로 병목이 실증되기 전까지 채택하지 않는다.**

| 후보 | 이유 |
|---|---|
| Kafka(auctionId 파티션 키) | 파티션당 단일 컨슈머로 순차 처리해 락 대기를 없앰. 처리량은 가장 좋으나 신규 인프라 도입 비용 큼 |
| Redis + Lua(ZSET) | Lua 스크립트는 Redis 싱글스레드 실행으로 원자적 처리 가능(현재가 체크+갱신을 한 번에). 이미 쓰는 Redis 재사용이라 Kafka보다 이 팀 스택에 맞음. 단, (a) Redis가 DB에 flush되기 전 죽으면 유실 위험이 있어 Streams(consumer group)로 최소 1회 보장이 필요하고, (b) Wallet 검증과 홀드는 Lua 안에 넣을 수 없으므로 [../wallet/5-auction-wallet-integration.md](../wallet/5-auction-wallet-integration.md)의 동기 `WalletPort` 트랜잭션을 별도로 유지해야 함 |

## 미정 항목 (팀 논의 필요)

> 회의로 해소된 항목(`global.realtime` 소유자, 배포 인스턴스 수, Redis Pub/Sub 채택 여부, SSE 목록 구독 전략, 티켓 vs `fetch`)은 제거했다.

- [ ] SSE 재연결 백필 정책(유실분 복구 안 함 vs 짧은 리플레이 버퍼)
- [ ] 이번 스프린트(P0)에 경매목록/상세/대시보드/알림 SSE 중 몇 개까지 넣을지
- [ ] CDN 적용 대상 최종 리스트
- [x] SSE payload 스키마(실제 JSON 필드) — 경매 목록과 대시보드가 REST 재조회 없이 렌더링할 수 있는 3종 스냅샷 계약
- [ ] Redis+Lua 핫패스 전환 트리거 기준(어느 정도 트래픽/지연이면 전환할지)
- [ ] 동시성 검증 테스트 전략
