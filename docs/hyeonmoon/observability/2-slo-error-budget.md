# SLO / Error Budget 정의

**배경:** 지금까지 부하테스트 결과를 볼 때 "성공/실패"를 상태코드 하나로만
판단해서, 정상적인 가격 경합(400 최소가 미달, 409 아이덤포턴시 충돌)까지
실패로 잡히는 문제가 있었다. 또 레이턴시 목표가 엔드포인트 성격을 반영하지
않고 뭉뚱그려져 있었다. 이 문서는 엔드포인트 카테고리별 SLO와, 실패를
분류하는 기준을 정한다.

## 실패·포화 신호 3종 (Four Golden Signals에 맞춘 분류)

| 분류 | 정의 | 예시 | SLO 가용성에 포함? |
|---|---|---|---|
| 명시적 실패 | 서버가 스스로 처리 실패를 인지하고 응답 | 5xx, 예외 | **포함** — 유일한 하드 실패 판정 기준 |
| 정책적 실패 | 비즈니스 규칙에 따른 정상 거부 | 400(최소가 미달), 409(경합 충돌), 401 | **미포함** — 단, 별도 SLI로 계속 추적 |
| 실행 포화 | SSE executor 큐가 차서 `RejectedExecutionHandler`가 호출됨 | `CallerRuns`로 요청 스레드가 브로드캐스트 작업을 대신 실행 | **미포함** — 이벤트는 드랍되지 않지만 요청 지연을 키우므로 Saturation SLI로 추적 |

SSE executor는 `DiscardPolicy`가 아니라 `CallerRuns`를 사용한다. 따라서 큐 포화가
발생해도 해당 태스크는 호출 스레드에서 끝까지 실행되어 구조적으로 조용한 드랍이
발생하지 않는다. 포화 횟수와 CallerRuns 소요시간은 Errors가 아닌 Saturation에서
확인한다. 개별 `SseEmitter.send()` 실패는 기존 전송 실패 메트릭으로 별도 관찰한다.

정책적 실패를 가용성에서 제외하는 이유: 두 사용자가 동시에 입찰하면 시스템이
아무리 빨라도 한쪽은 거부된다 — 이건 서비스 품질 문제가 아니라 경매 구조
자체의 본질이다. 다만 "가격 정보를 늦게 뿌려줘서 낡은 가격 기준으로 입찰했다
거부되는" 경우는 실시간성 문제일 수 있어, 정책적 실패율이 경합 상황 대비
비정상적으로 튀는지는 별도 SLI로 계속 감시한다.

## SLO 윈도우

30일 rolling 같은 상시 운영 개념 대신 **부하테스트 세션 하나**를 윈도우로
잡는다. 이 프로젝트는 상시 트래픽이 아니라 세션 단위로 부하를 가하는
구조이기 때문에, "이번 세션 동안 실패율이 예산 안에 있었는가"를 보는 용도로
축소해서 쓴다.

## 엔드포인트 카테고리별 목표

세분화 기준(아래 3가지를 모두 만족할 때만 별도 카테고리로 쪼갠다):

1. 하위 항목끼리 실제로 지연/실패 양상이 다르다
2. 합쳐서 보면 한쪽 문제가 다른 쪽에 가려진다
3. 어느 쪽이 문제인지에 따라 대응 방법이 실제로 달라진다

이 기준으로 "bid-context"를 "일반조회"에서, "auction-SSE"를 "notification-SSE"에서
분리했다(각각 지연 분포와 실패 모드가 실측으로 다르게 나왔다). 정책적 실패를
원인(400 vs 409)으로 나눠 **대응 방법을 다르게 가져가는 것**은 지금은
보류한다(둘 다 "정상 거부"로 같은 취급). 다만 아래처럼 **레이턴시는 상태코드별로
반드시 나눠서 봐야 한다** — 이건 별도 세분화가 아니라 "성공/실패 레이턴시
분리"라는 기존 원칙을 상태코드 단위까지 그대로 적용한 것뿐이다.

### 입찰 쓰기 — 상태코드별 레이턴시 (성공/실패를 이분법으로 뭉치면 안 되는 이유)

`AuctionCommandService`는 `findByIdForUpdate`(row 락 획득)를 **제일 먼저**
실행하고, 그다음에 가격 검증을 한다. 즉 400(최소가 미달)으로 거부되는
요청도 락 대기(`dbidding_auction_lock_wait_seconds`)는 201(성공)과 **똑같이
겪는다** — hold/outbid/save/publish 단계만 스킵할 뿐이다. "실패 응답은 DB를
안 타서 당연히 빠르다"는 가정은 락 경합이 없을 때만 맞다.

2026-08-10 실측(`POST /api/auctions/{auctionId}/bids`, 상태코드별, 24h):

| 상태 | p50 | p95 | p99 |
|---|---|---|---|
| 201(성공) | 377ms | 774ms | 960ms |
| 400(가격 거부) | 160ms | 382ms | 581ms |
| 409(충돌) | 8ms | 221ms | 223ms |
| 500(에러) | 469ms | 789ms | 867ms |

p50만 보면 400이 201보다 2배 넘게 빠르지만, **p99로 가면 격차가 좁혀진다**(581ms vs
960ms, 400이 201의 60% 수준) — 락 경합이 심한 꼬리 구간에서는 거부돼도 별로
안 빠르다는 뜻이다. 그래서 "입찰 쓰기" 카테고리의 p95/p99 목표는 상태코드
전체를 섞은 값이 아니라 **성공(201)과 정책적 거부(400/409)를 각각** 재서
비교해야 한다 — 섞으면 성공 경로의 진짜 비용이 거부 응답에 의해 희석되어
보인다. 이 분리는 `http_server_requests_seconds_bucket`의 기존 `status`
라벨만 쓰면 되므로 신규 계측 없이 대시보드 쿼리 수준에서 바로 적용 가능하다
([`5-grafana-dashboard-redesign.md`](5-grafana-dashboard-redesign.md)의
Latency 섹션에 반영).

| 카테고리 | 가용성 목표(5xx 기준) | p95 목표 | p99 목표 | 비고 |
|---|---|---|---|---|
| 인증(`/api/auth/login`, `/refresh`) | 99.9% | 500ms | 900ms | 2026-08-10 실측 p95 1.41s/p99 1.92s로 크게 미달 — PBKDF2 비용 × 인프라(t4g.micro) 문제, [`../auth/6-password-hash-cost-tuning.md`](../auth/6-password-hash-cost-tuning.md) 참고 |
| 입찰 쓰기 — 성공(201) | 99%(5xx만) | 800ms | 1s | 위 상태코드별 표 참고. hold/outbid/save/publish 전체 경로 |
| 입찰 쓰기 — 정책적 거부(400/409) | - | 400ms | 600ms | 락 대기까지만 겪는 경로. 이 목표를 크게 벗어나면 락 경합 심화 신호 |
| bid-context(`GET .../bid-context`) | 99.5% | 200ms | 350ms | 실측 p95 321ms/p99 446ms |
| 일반조회(목록/상세/통계) | 99.5% | 300ms | 600ms | 실측 p95 380ms/p99 **1.52s** — 꼬리가 김, 원인 조사 필요 |
| auction-SSE 연결 수립 | 99% | 500ms | 1s | 계측 없음 — [`4-metrics-gap-and-instrumentation.md`](4-metrics-gap-and-instrumentation.md)에서 추가 후 확정 |
| notification-SSE 연결 수립 | 99% | 800ms | 1.5s | 티켓 발급 단계가 하나 더 있어 auction보다 여유를 둠. 계측 없음 — 같은 문서에서 추가 후 확정 |
| SSE 이벤트 end-to-end 전달 | - | 300ms | 600ms | 지금 있는 `dbidding_auction_sse_send_duration_seconds`는 서버 `send()` 호출 자체만 재서(p99 3ms) 이 목적엔 못 씀 — 같은 문서에서 클라이언트 수신 시각까지 포함한 계측 추가 후 확정 |

## 참고

- 실측치는 2026-08-10 기준, Redis 도입 전 organic 트래픽 24시간 집계다.
  세션 단위로 통제된 정식 기준선은 [`3-redis-baseline-comparison.md`](3-redis-baseline-comparison.md)에서
  별도로 잡는다.
- 로그인 목표(p95 500ms)는 업계 관행(Google RAIL, 일반적인 로그인 API
  p95 300~500ms) 기준이며, 지금 인프라로는 달성 못 한다는 걸 알고 잡은
  지향점이다. 인스턴스 업그레이드와 PBKDF2 반복횟수/알고리즘 조정이 선행
  과제다.
