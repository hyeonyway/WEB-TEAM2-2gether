# 인증 성능 개선 방향

**배경:** 부하테스트 중 로그인 API 레이턴시가 p50 1.15s/p95 1.41s/p99 1.92s로
실측됐다. 원인은 `PasswordHasher`의 PBKDF2WithHmacSHA256 반복횟수
600,000회(`1-entity.md`~`3-login-and-token.md` 구현 당시 OWASP 2023 권고를
그대로 채택한 값)가 backend 호스트(`t4g.micro`, 2vCPU)에서 CPU 바운드로
느리게 도는 것이다. 보안 설계 자체는 올바르며, 인프라(약한 CPU)와의 조합이
문제다.

## 선택지

| 방법 | 효과 | 트레이드오프 |
|---|---|---|
| 반복횟수 낮추기(예: 21만, OWASP 이전 권고치) | 즉시 ~2.8배 개선 | 보안 마진 축소, 팀 합의 필요 |
| PBKDF2 → Argon2id 전환 | 구조적으로 더 효율적, GPU/ASIC 공격에도 강함 | 메모리 사용 알고리즘이라 903MB RAM 박스에서 동시 로그인 시 새 메모리 압박 가능 — 인스턴스 업그레이드 후 검토 |
| 해싱을 전용 bounded executor로 분리 | 로그인 몰릴 때 Tomcat 워커스레드 고갈 방지(다른 API 안 끌려 내려감) | 개별 요청 체감속도는 그대로, 처리량/격리만 개선 |
| 인스턴스 업그레이드 | CPU 바운드 연산이라 코어 늘면 비례 개선 | 별도 인프라 이슈(이 문서 범위 밖) |

**권장 순서:** 해싱 executor 분리(빠르고 안전, 즉시 가능) → 인스턴스
업그레이드(별도 이슈) → CPU 여유 생기면 Argon2id 전환 검토. 반복횟수
낮추기는 보안 후퇴라 팀 동의 없이는 실서비스에 적용하지 않는다.

## 현재 상태와 문제

현재 데모·부하테스트를 위해 반복 횟수가 100회로 코드 상수에 고정돼 있다.
이 방식은 다음 문제가 있다.

- 운영으로 전환할 때 안전한 600,000회를 복원하려면 코드 수정·재빌드·재배포가
  필요하다.
- 같은 이미지로 운영과 데모를 실행할 수 없고, 배포 환경이 어떤 비용을 쓰는지
  설정만 보고 판단할 수 없다.
- PBKDF2 해시에 반복 횟수를 함께 저장하지 않으므로, DB에 저장된 해시의 생성
  기준과 런타임 설정이 달라지면 로그인 검증이 실패한다.

## 반복 횟수 환경 설정 분리

반복 횟수는 다음 설정으로 주입한다.

```yaml
app:
  password-hash:
    iterations: ${PASSWORD_HASH_ITERATIONS:600000}
```

| 환경 | `PASSWORD_HASH_ITERATIONS` | 목적 |
|---|---:|---|
| 운영·기본 실행 | 미설정 (600,000) | OWASP 기준 비용을 기본으로 유지 |
| 데모·k6 부하테스트 | `100` | 해싱 CPU 비용이 시나리오 결과를 지배하지 않게 함 |
| 단위 테스트 | 테스트 속성으로 최소값 지정 | 테스트 시간을 짧게 유지 |

`PasswordHasher`는 이 값을 생성자 주입받는다. 값은 정수이고 1 이상이어야 하며,
0·음수·숫자가 아닌 값은 애플리케이션 시작 단계에서 실패시킨다. 600,000 미만
값은 데모 전용이라는 운영 경고를 남기는 것을 검토한다.

## 해시·설정 동기화 규칙

반복 횟수는 단순 성능 토글이 아니다. 현재 해시 형식은 salt와 hash만 저장하고
반복 횟수를 저장하지 않으므로, 한 DB를 사용하는 애플리케이션 인스턴스는 모두
같은 값을 사용해야 한다.

1. `PASSWORD_HASH_ITERATIONS`를 변경하기 전에 영향을 받는 계정의 원문
   비밀번호를 확인한다.
2. 같은 salt·새 반복 횟수로 해시를 재계산해 시드 SQL 또는 데이터 마이그레이션에
   반영한다.
3. 설정 변경과 해시 변경을 같은 배포 단위로 적용한다. 둘 중 하나만 먼저
   배포하면 기존 사용자가 로그인하지 못한다.
4. 새 회원가입과 비밀번호 변경은 새 설정으로 해시를 생성한다.

기존 해시마다 서로 다른 반복 횟수를 지원하거나 단계적 마이그레이션이 필요해지면,
향후에는 해시 문자열에 알고리즘·반복 횟수 버전을 함께 저장하는 별도 개선 이슈로
다룬다. 이번 범위는 환경 전체가 하나의 반복 횟수를 공유하는 방식으로 한정한다.

## 데모 프로젝트용 시드 계정

데모·부하테스트 환경은 `PASSWORD_HASH_ITERATIONS=100`을 명시하고, k6 계정
5만 개의 해시도 100회 기준으로 둔다.

**같이 바뀌어야 하는 파일:**
- `backend/src/main/resources/application.yml` — `app.password-hash.iterations`
  기본값과 `PASSWORD_HASH_ITERATIONS` 바인딩.
- `backend/src/main/java/com/dbidding/account/password/PasswordHasher.java` —
  상수 대신 설정값 주입.
- `backend/src/main/resources/required-data/002-user.sql` — k6 계정
  5만 개(`k6-user00001`~`k6-user50000`)의 `encrypted_password`는 100회
  기준이다. 데모값을 바꾸면 같은 비밀번호(`K6LoadTest123!`)·같은 salt로
  해시를 재계산해야 한다.
- `id=1`(`dbidding@dbidding.com`) 계정은 원래 비밀번호를 문서 어디에도
  남겨두지 않아 재계산이 불가능하다 — 이 계정의 로그인은 반복횟수를
  100으로 둔 환경에서 보장되지 않는다. 이 계정을 데모 로그인에 쓸 경우
  먼저 알려진 비밀번호로 재설정하고 해당 반복 횟수 기준 해시를 시드에 반영해야
  한다. **(2026-08-11 반영 완료)** 비밀번호를 `Dbidding123!`로 재설정하고
  같은 salt로 100회 기준 해시를 재계산해 `002-user.sql`에 반영했다
  (#379).

**배포 환경 확인 필요:** 이 문서 작성 시점(2026-08-11) 기준 prod
`docker-compose.yml`에는 `PASSWORD_HASH_ITERATIONS`가 전혀 설정돼 있지
않다. main은 아직 반복횟수가 코드 상수(100)로 고정된 버전이라 문제없지만,
이 설정 분리 기능이 들어간 `dev`가 main에 머지·배포되면 미설정 시 기본값
600,000이 적용돼 **기존 100회 기준 해시(위 계정들 포함) 전부 로그인이
깨진다.** `dev→main` 배포 전에 `docker-compose.yml`에
`PASSWORD_HASH_ITERATIONS: "100"`을 반드시 추가해야 한다.

## 복원 계획

실서비스 전환 전에는 환경변수를 제거하거나 600,000으로 설정하고, 실제
운영 계정·시드 데이터가 같은 기준으로 해시돼 있는지 확인한다. 데모 계정의
100회 해시는 운영 DB에 반입하지 않는다.
