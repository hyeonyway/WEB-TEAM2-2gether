# 이슈 5: 인증 모드 성능 비교와 장애 실험

## 1. 이슈 경계

- 선행 문서: [`4-redis-session-multi-instance.md`](4-redis-session-multi-instance.md)
- 목표: JWT·인메모리 세션·Redis 세션을 같은 기능과 환경에서 측정
- 산출물: 원시 결과, 비교 표·그래프, 장애 실험 기록, 최종 선택 권고안
- 비목표: 이 이슈 안에서 미선택 구현 삭제
- 후속 문서: [`6-final-selection-and-cleanup.md`](6-final-selection-and-cleanup.md)

성능 수치만으로 기술을 선택하지 않는다. 기능·보안 보장, 장애 영향, 운영 복잡성을 함께 비교한다.

## 2. 기준선 확보

구조 변경 전 또는 비교 가능한 기준 커밋에서 다음을 확보한다.

- 로그인·Refresh Rotation·로그아웃 테스트 결과
- `@CurrentUser` 통합 테스트 결과
- 공개·개인화 SSE 인증 테스트 결과
- 인증 없이 입찰할 수 없는지 확인한 결과
- JWT 인증을 포함한 TPS·p50·p95·p99·CPU
- 사용한 커밋 SHA와 실행 환경

기존 테스트 실패가 있으면 인증 전환 실패와 구분할 수 있게 목록과 원인을 기록한다.

## 3. 비교 모드

최소 비교 대상은 다음 세 가지다.

1. JWT 로컬 서명 검증
2. 인메모리 HttpSession
3. Redis HttpSession

즉시 무효화 비용까지 비교하려면 다음을 별도 실험 모드로 추가한다.

4. JWT + Redis denylist 직접 조회
5. JWT + 로컬 denylist 캐시와 Redis 변경 전파

4·5를 실제 구현하지 않았다면 추정 처리량이나 지연을 결과 표에 넣지 않는다.

## 4. 공정한 보안 조건

| 비교 모드 | 즉시 무효화 | 정상 요청의 외부 조회 |
|---|---:|---:|
| JWT 로컬 검증 | Access 만료 전 불가 | 없음 |
| JWT + Redis denylist | 가능 | 매 요청 Redis |
| JWT + 로컬 denylist 캐시 | 전파 수준에 의존 | 정상 요청은 로컬 |
| 인메모리 세션 | 단일 인스턴스에서 가능 | 없음 |
| Redis 세션 | 가능 | 매 요청 Redis |

JWT 로컬 검증과 Redis 세션의 처리량만 나란히 놓고 동일한 보안 보장이라고 설명하지 않는다. 최종 발표에는 어떤 보안 수준끼리 비교했는지 명시한다.

## 5. 실행 조건

- 같은 애플리케이션 코드 커밋
- 같은 JVM·CPU·메모리 제한
- 같은 애플리케이션 인스턴스 수
- 같은 DB·Redis 네트워크 위치
- 같은 사용자·경매 데이터
- 같은 입찰 분포와 동시성
- 로그인은 사전 단계에서 수행하고 측정 구간에서 제외
- 충분한 warm-up 후 동일 시간 측정
- 모드별 최소 3회 반복
- GC, CPU throttling, 오류율 동시 기록
- 실행 순서를 교차해 캐시·시간대 편향 축소

하나의 사용자나 세션만 재사용하지 않는다. 목표 사용자 수만큼 독립된 Access Token 또는 Session ID를 만들고 Redis key cardinality와 메모리를 측정한다.

## 6. 부하 모델

TPS를 먼저 정하지 않고 사용자 행동 시나리오를 먼저 정의한다.

예시:

- 등록 사용자 수: 10,000명
- 평시 동시 사용자: 300명
- 경매 마감 직전 동시 사용자: 1,000명
- 마감 10초 전 활성 사용자의 20%가 입찰 시도
- 사용자는 입찰 전 대시보드 또는 경매 상세 조회
- 개인화 SSE 연결은 로그인 사용자당 1개

최종 수치는 서비스 예상과 기존 로그가 있을 경우 그 근거로 조정한다. 결과 문서에는 숫자와 함께 근거를 남긴다.

## 7. 시나리오

### A. 일반 보호 조회

대시보드·지갑 잔액 같은 읽기 요청으로 인증 자체의 상대 비용을 본다. DB 조회 비용이 크면 인증 시간도 별도 측정한다.

### B. 마감 직전 입찰

경매 행 락과 지갑 hold가 포함된 핵심 경로에서 인증 비용이 전체 지연의 어느 비율인지 본다. 입찰 성공·상위 입찰 충돌·잔액 부족을 실제 비율로 섞는다.

### C. 개인화 SSE

동시 연결 수, heartbeat, 재연결, 인증 확인, Redis 연결 수를 측정한다. 연결 수립 비용과 이벤트 fan-out 비용을 분리한다.

### D. 로그인과 인증 복구

JWT 로그인·Refresh와 세션 로그인·현재 사용자 복구를 비교한다. 핵심 요청과 별도 결과로 기록한다.

### E. 로그아웃·강제 만료

로그아웃 또는 계정 정지 후 다른 인스턴스 요청과 이미 열린 SSE가 차단되기까지 걸린 시간을 측정한다.

## 8. 장애 실험

| 장애 | 확인할 항목 |
|---|---|
| Redis 응답 지연 | timeout, thread 고갈, p99, fail-closed |
| Redis 연결 거부 | 보호 API와 공개 API의 분리 |
| Redis 재시작 | 세션 유실과 재로그인, 사용자 오인 여부 |
| 애플리케이션 한 대 종료 | 세션 유지와 SSE 재연결 |
| DB 지연 | JWT Refresh와 공통 로그인 영향 |
| Pub/Sub 메시지 유실 | SSE heartbeat·재연결에서 무효 세션 차단 |

장애 실험은 운영 환경을 직접 손상하지 않는 격리된 환경에서 수행한다. 주입 시작·종료 시각과 대상, 예상 결과를 미리 기록한다.

## 9. 측정 지표

| 분류 | 지표 |
|---|---|
| 사용자 체감 | p50, p95, p99, 최대 응답 시간 |
| 처리량 | 요청 TPS, 입찰 TPS |
| 안정성 | 성공률, 4xx·5xx, timeout |
| 애플리케이션 | CPU, heap, GC pause, thread 수 |
| Redis | ops/sec, command latency, 연결 수, memory, key 수 |
| 인증 | 인증 단계 시간, 서명 실패, 세션 lookup 실패 |
| 보안 | 로그아웃·정지 후 잘못 허용된 요청 수 |
| SSE | 동시 연결, 재연결, 이벤트 유실·중복, emitter 정리 |

평균값만으로 결론을 내리지 않는다. 입찰과 SSE는 tail latency와 오류 분포를 함께 본다.

## 10. 결과 형식

각 실행은 다음 메타데이터를 가진다.

```text

auth_mode:

denylist_mode:

redis_environment:

```

원시 결과를 보존하고 같은 스크립트로 표와 그래프를 재생성할 수 있게 한다. 가장 좋은 한 번만 선택하지 않고 반복 결과의 중앙값과 변동을 제시한다.

## 11. 판정 기준

다음 기준을 모두 검토한다.

1. P0 기능과 보안 완료 여부
2. 목표 부하에서 p95·p99와 오류율
3. 로그아웃·계정 정지 반영 시간
4. 개인화 SSE 복잡성과 복구 동작
5. Redis 장애의 영향 범위
6. 운영·모니터링 비용
7. 코드와 테스트 복잡성
8. 미래 도메인 분리 가능성

성능 차이가 작으면 더 단순하고 보안 통제가 명확한 방식을 우선한다. JWT가 유의미하게 빠르면 Refresh·denylist·ticket 유지 비용과 함께 평가한다.

## 12. 완료 기준

- 모든 모드가 같은 코드·환경·데이터에서 최소 3회 실행된다.
- 보안 보장 차이가 결과 표에 표시된다.
- 정상 부하와 Redis 장애 실험 결과가 모두 존재한다.
- 잘못 허용된 보호 요청 수가 별도 지표로 기록된다.
- 원시 데이터와 재현 가능한 실행 명령이 남는다.
- 최종 선택을 위한 권고안에 수치와 운영 근거가 함께 제시된다.
