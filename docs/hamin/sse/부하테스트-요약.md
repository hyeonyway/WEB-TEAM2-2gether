## 50 rps 불안정성 조사 (2026-08-13)

RATE=50을 3번 돌렸는데 1번은 클린(00:05), 2번은 고갈(00:31, 00:39) — 같은 RATE에서 결과가 갈린다. 배제한 것과 남은 후보:

**배제됨**
- gap lock/인덱스 누락 → `db-lock-diag-results/20260813T003924-db-locks.log`에서 실제 쿼리 확인, `auctions` PK에 순수 X record lock 하나뿐
- `innodb_deadlock_detect` 오버헤드 → OFF로 바꿔도 동일 재현 (앞서 확인)
- wallet_holds 누적(유저당 900~1200건) → `performance_schema.events_statements_summary_by_digest` 확인 결과 지금도 평균 0.1~0.7ms로 빠름
- backend JVM GC/힙 누수 → 고갈 실행의 G1 Old Gen 사용량이 오히려 더 낮았음

**남은 후보 (우선순위 순, → 결과)**
1. 자기강화적 큐잉(임계 이용률 근처의 불안정성) → 부차적 요인으로 강등(아래 확정 원인의 증상일 뿐)
2. 세션 전체에 걸쳐 트랜잭션당 처리 시간이 서서히 증가 → **확정** (검증: 새 경매 2000002로 재현, 아래 참고)
3. Redis pub/sub 잔여 부하 누적 → 미확인 상태로 종료(원인이 이미 확정돼서 추가 조사 안 함)

## 원인 확정: `bids` 조회 쿼리의 filesort가 auction별 누적 입찰 수에 선형으로 느려짐

**검증**: 새 경매 2000002(bid 이력 0건)로 RATE=50을 2번 실행 → 둘 다 클린 (HikariCP active 3~5/pending 0, MySQL CPU 0.57~0.64 core, Com_commit 87.7~88/s 역대 최고). 3000009(6,800+건 누적)와 정반대 결과로, "경매별 누적 입찰 수"가 진짜 변수임을 확정.

**메커니즘** (`performance_schema.events_statements_summary_by_digest` + `EXPLAIN`으로 확인):

```sql
-- 최고가 조회 (① 락 안 / ② 읽기 경로, 둘 다 status만 다름)
SELECT ... FROM bids WHERE auction_id=? AND status=?/IN(...)
  ORDER BY bid_price DESC, created_at LIMIT 1
-- ③ 입찰 내역 페이지네이션 (읽기 경로)
SELECT ... FROM bids WHERE auction_id=?
  ORDER BY created_at DESC, id DESC LIMIT ?
```

`EXPLAIN` 결과 셋 다 `key: idx_bids_auction_id`, `Extra: Using filesort`, `rows: 7080`(3000009 기준). `idx_bids_auction_price(auction_id, bid_price)` 인덱스가 있는데도 `status`(①②) 또는 `created_at`(③)이 어떤 인덱스에도 같이 안 걸려 있어서, **그 auction_id에 해당하는 모든 row를 긁어와 메모리에서 재정렬**한 뒤 `LIMIT`으로 1~5개만 자름. 실측: 3000009 기준 평균 1.6~16.4ms, 최대 119~613ms, 호출당 평균 2,638~2,676행 스캔(반환은 1~5행뿐).

①(`highestBid()`)은 **`auctions` row의 `FOR UPDATE` 락을 쥔 트랜잭션 안에서** 실행되므로 락 보유 시간이 누적 입찰 수만큼 늘어나고, 단일 row 직렬화 구조라 그 증가분이 큐 폭증으로 증폭됨. ②③은 락 밖(읽기 경로)이라 락 보유엔 안 걸리지만 요청 자체의 latency를 직접 늘림. 티핑포인트는 이 환경(2 vCPU, RATE=50) 기준 **대략 2,100~7,000건 사이**.

### 인덱스 처방 및 ORDER BY 필요성 검토

`Bid.java`의 `markOutbid()`/`markWon()`을 보면 새 입찰이 들어올 때마다 이전 `LEADING` bid를 즉시 `OUTBID`로 바꾸고, 낙찰 시에만 `LEADING`→`WON`으로 전환한다. 즉 **경매 하나당 `status=LEADING`인 row는 항상 0개 아니면 1개, `status IN (LEADING, WON)`도 항상 0개 아니면 1개** — 애초에 여러 개 나올 수 없다.

- **①②는 `ORDER BY`가 사실상 장식**: 결과가 원래 1개뿐이라 정렬할 대상이 없음. 느린 이유는 "정렬을 못해서"가 아니라 "`status` equality 필터에 인덱스가 없어서 정렬할 필요도 없는 후보를 다 긁어모으고 있는 것". → `CREATE INDEX idx_bids_auction_status ON bids (auction_id, status);` 하나면 바로 그 1개 row로 꽂혀서 `bid_price`/`created_at` 정렬 자체가 필요 없어짐. `idx_bids_auction_price`는 이 인덱스 추가 후 실질적으로 안 쓰이게 될 가능성 높음(사용 여부 확인 후 정리 대상).
- **③은 진짜 정렬이 필요함**: 입찰 내역을 최신순으로 페이지네이션하는 목록 조회라 결과가 여러 건이고 시간순 정렬이 실제 요구사항. → `CREATE INDEX idx_bids_auction_created ON bids (auction_id, created_at DESC, id DESC);`로 정렬을 인덱스가 대신하게(covering) 해야 함.

**결론**: 근본 원인은 RATE나 임계 이용률이 아니라 **`bids` 테이블에 `(auction_id, status)` / `(auction_id, created_at DESC, id DESC)` 복합 인덱스가 없는 것**. 다음 검증 스텝은 이 두 인덱스를 추가한 뒤 3000009(7,000+건 누적된 경매)로 RATE=50~200을 다시 돌려 filesort가 없어지고 문제가 해소되는지 확인하는 것.

# 인덱스 수정 후 (`test/bids-auction-index-fix` 브랜치, 이슈 없이 테스트 전용)

`schema.sql`에 `idx_bids_auction_status (auction_id, status)`, `idx_bids_auction_created (auction_id, created_at DESC, id DESC)` 추가하고 안 쓰는 `idx_bids_auction_price` 제거. `required-data`의 `003`/`004` OPEN 경매도 즉시낙찰가 NULL·종료시각 7일로 수정(즉시낙찰 조기 종료 방지). 2000002에 SQL로 7,194건 강제 누적(`LEADING` 1개로 정리) 후 재검증.

### 메모리 누수 의심 → 재시작으로 검증

backend 프로세스가 01:40에 뜬 이후 오늘 테스트를 15번+ 재시작 없이 누적해서 돌렸는데, JVM RSS가 698MB(힙 캡 384MB의 거의 2배)까지 올라가 있었고 컨테이너 메모리도 902.4/903MB(99.93%)로 꽉 차 있었음 — SSE 연결(매 테스트 300+300개)이 서버 쪽에서 완전히 정리 안 되고 누적되는 게 아닌지 의심해서 backend를 재시작해 검증:

- **재시작 직후(콜드) RATE=130**: median 2,965ms로 오히려 훨씬 나빠짐 — JIT 콜드 스타트 효과가 지배적이라 이 비교 자체는 무효.
- **웜업(RATE=100 1회) 후 RATE=130**: median 142ms, pending 파도 1번뿐(재시작 전엔 2번, median 346ms) — **확실히 개선됨.**

**결론**: 누적된 상태(메모리 관련 뭔가)가 결과를 "더 나쁘게" 만들고 있었던 건 맞지만(파도 2번→1번, latency 346→142ms), **그 밑바탕에 있는 backend CPU/GC 캡 자체는 누적 artifact가 아니라 이 RATE 수준이 실제로 요구하는 비용**이다. 즉 원인이 두 개 겹쳐 있었음:
1. (해소됨) 장시간 누적 테스트로 인한 JVM 메모리/GC 상태 악화 — 재시작으로 리셋 가능
2. (해소 안 됨) backend 컨테이너 2 vCPU 캡 자체의 처리 한계 — RATE 자체를 낮추거나 CPU를 늘리거나 코드/GC 튜닝 없이는 해결 안 됨

# SSE executor/연결 메트릭 반영 후 베이스라인 (2026-08-14)

[#458](https://github.com/softeerbootcamp-8th/WEB-TEAM2-2gether/pull/458)로 SSE executor task lifecycle 메트릭(`executor_active_threads` 등, Spring Boot 자동 계측)과 연결 종료 원인·지속시간 메트릭(`dbidding_sse_connections_closed_total` 등)이 추가됨. 이제 `run-k6.sh`가 매 실행마다 `serverMetrics.duringTest`로 이 지표들을 결과 JSON에 자동으로 남긴다(수동 Grafana/curl 조회 불필요) — 상세는 `run-k6.sh`(로컬 부하테스트 저장소 `~/dbidding-loadtest-local`, 이 코드 저장소 밖) 참고.

**측정 방식 변경 요약**:
- `duringTest`: `[테스트 시작, 종료]` 구간만, 종료 시점에 즉시(대기 없이) 평가 — k6가 duration 끝나며 남은 VU를 한꺼번에 끊어서 생기는 send_failure 몰림(heartbeat 25s+scrape 15s 지연 후 감지됨)이 자동으로 빠짐. **아래 표의 SSE 지표는 전부 이 `duringTest` 기준.**

# SSE_VUS 단계별 backend CPU 실험 (RATE=130 고정, 2026-08-14)

"SSE가 backend CPU를 얼마나 먹는지 알아내서, bid 처리에 필요한 CPU 여유를 남겨두는 수준으로 SSE 구독자 수를 제한/밸런싱하자"는 목표에 따라 RATE=130 고정하고 SSE_VUS만 0→50→100→200으로 단계적으로 올림. `containerCpu` 자동 수집(위 섹션 참고) 덕에 매 실행 결과 JSON에서 바로 확인 가능.

**핵심 발견 — SSE_VUS 0→50 사이에 완전한 절벽(cliff)**: SSE 구독자가 0명일 땐 backend/MySQL 둘 다 CPU 여유가 넘치고(0.64/0.71 core) bid_accepted도 55.6%로 압도적으로 높은데, **구독자를 단 50명만 붙여도 backend와 MySQL이 동시에 거의 풀캡(1.95/1.97 core)까지 치솟고 bid_accepted가 8.96%로 급락**한다. 0→50 사이의 완만한 곡선이 아니라 계단식 절벽.

**⚠️ SSE_VUS=50 수치는 콜드 스타트 오염 가능성이 높아 확정 금지**: SSE_VUS=0 실행은 emitter 등록/브로드캐스트 코드 경로를 아예 안 타므로 JIT가 그 경로를 컴파일할 기회가 없다. 그 다음 실행(SSE_VUS=50)이 이 백엔드 프로세스 생애주기에서 **처음으로 SSE 브로드캐스트 코드를 실제로 타는 순간**이라, 이전에 여러 번 문서화된 "재시작 직후 콜드 스타트로 수치가 왜곡됨" 패턴과 정확히 같은 함정일 수 있다. 실제로 SSE_VUS=50(HikariCP 30/14 고갈, MySQL 1.97 core)이 SSE_VUS=100(16/0 고갈 없음, MySQL 1.66 core)보다 오히려 더 나쁘게 나온 것 — 구독자가 더 적은데 더 나쁜 건 "50이 진짜 임계점"이 아니라 "50이 콜드 경로였다"는 쪽으로 강하게 기운다. **다음: SSE_VUS=50을 웜업 라운드(예: SSE_VUS=10 한 번 버리는 실행) 이후에 재실행해서 재현되는지 확인 필요.**

**그래도 확실한 것**: SSE_VUS=0(완전 클린)과 SSE_VUS=50 이상(backend CPU 풀캡) 사이엔 명백한 단절이 있다 — 즉 "SSE와 입찰 API 간 backend CPU 밸런싱"이라는 목표가 유효하다는 것 자체는 이번 실험으로도 재확인됨. 다만 그 밸런싱을 걸 지점이 "50 근처"인지 "0과 50 사이 어딘가(예: 10, 20)"인지는 콜드 스타트를 배제한 재실험 전까진 특정할 수 없음.

**SSE_VUS=200 추가 후 — 50이 콜드 스타트였다는 게 사실상 확정**: MySQL CPU가 50(1.97)→100(1.66)→200(1.25)로 SSE_VUS와 무관하게 계속 낮아지는 추세(오히려 반비례)인 반면, **backend CPU는 100/200/300/1000 전부 1.92~2.00 core로 사실상 평평한 상수**다. 50만 유독 MySQL까지 같이 튀었던 건 SSE 부하 자체의 함수가 아니라 그 실행이 "이 프로세스 최초의 SSE 실행"이었다는 타이밍 문제였다는 뜻 — **50 이후의 재실험(웜업 후 재현 확인)은 우선순위를 낮춰도 됨**, 이미 100/200/300/1000의 일관된 패턴으로 답이 나왔음.

**결론(RATE=130 기준)**: backend CPU는 **SSE_VUS=100 근처에서 이미 cap(2 core)에 도달하고, 그 이후(100→1000)로는 SSE_VUS를 더 올려도 backend CPU/bid_accepted가 거의 안 변한다**(bid_accepted 8.96~10.3% 사이서만 오르내림). 즉 backend CPU 병목은 "SSE_VUS가 얼마나 큰지"보다 "SSE 브로드캐스트 기능이 켜져 있는지 자체"에 훨씬 더 좌우된다 — 구독자 100명이든 1000명이든 이미 캡에 도달한 뒤라 차이가 별로 없다는 뜻. HikariCP pending은 0~30 사이서 실행마다 들쭉날쭉한데(100:0, 200:21, 300:0, 1000:20) backend CPU가 이미 평평하므로 이건 SSE_VUS의 함수가 아니라 DB row-lock 경합의 타이밍 노이즈로 보임(RATE=50 불안정성 조사 때와 같은 패턴).

**다음 우선순위 제안**: SSE_VUS를 더 잘게 쪼개서(10, 20, 30) "0과 100 사이 어디서 절벽이 시작되는지"를 좁히는 것보다, **"켜져 있으면 무조건 cap을 다 쓰는" SSE 브로드캐스트 자체의 CPU 비용을 줄이는 최적화(예: 이미 검증된 `sse-virtual-threads` 프로필, 이벤트 배칭/직렬화 최적화)** 쪽이 더 실질적인 다음 스텝으로 보임 — "SSE_VUS를 몇 명으로 캡할까"보다 "SSE 기능 자체를 더 싸게 만들 수 있는가"가 이 커브 모양(계단형)에 더 잘 맞는 질문.

**참고**: 네 실행 모두 `http_req_failed` 0건 — connection reset 등 HTTP 레벨 문제는 이번 실험 전체에서 없었음(CPU가 아무리 포화돼도 요청 자체는 끝까지 처리됨, 클라이언트 타임아웃/재시도 문제가 아니라 순수 latency 문제).

| e2e p95 | 1343ms | 1174ms | **720ms** |

**결론 — Redis Lua가 MySQL 쪽 병목을 완전히 없앴다**: DB 락 진단 로그에서 `active_trx`/`trx_in_lock_wait`가 테스트 내내 **한 번도 0을 벗어나지 않음** — 지금까지 문서 전체를 관통했던 "단일 auction row 직렬화" 문제 자체가 이 프로필에서는 존재하지 않는다. 그 결과 HikariCP도 20/0→7/0으로 훨씬 여유로워졌고, bid_accepted가 7~9%대에서 **22.5%로 3배 가까이 뛰었으며**, bid-context/bids p95 latency는 각각 2.5배·4.6배 개선됐다.

**그런데 backend CPU는 여전히 캡(2 core)에 그대로 포화돼 있다** — MySQL 병목을 없애도 SSE 브로드캐스트가 여전히 CPU를 다 쓰고 있어서, "backend CPU를 SSE와 bid 처리 사이에 어떻게 나눌까"라는 원래 목표는 그대로 유효하다. 다만 이제는 bid 처리 쪽이 DB 락 대기 없이 훨씬 가벼워졌으니(HikariCP 7/0), **같은 backend CPU 예산 안에서 SSE에 세마포어 캡을 걸어보는 실험의 효과가 훨씬 선명하게 드러날 조건**이 됐다.

**참고**: `RedisBidExecutor`는 `DbBidExecutor`와 달리 로그를 전혀 안 남긴다(`auction.bid.rejected` 같은 WARN이 없음) — `tail-logs.sh`/`app.log`가 이 프로필에서 조용한 건 정상이지 로깅이 고장난 게 아님.

**다음**: 이전에 논의한 세마포어 캡 실험(가상스레드 동시성 제한)을 이 Redis Lua 기반 위에서 진행하는 게 좋아 보임.

**결론 — 절벽은 RATE 1200~1300 사이, 매우 가파름**: 1200에서 backend CPU 1.86 core(아직 여유)였다가 1300에서 바로 2.00 core(완전 포화)로 튀고, median latency도 ms 단위에서 순식간에 1.7초대로 넘어간다 — 완만한 열화가 아니라 임계 이용률 근처에서 흔한 전형적 급락(cliff) 패턴. **포화 이후(1300~3000)로는 `http_req_failed`가 거의 안 오르고(0~0.02%) 대신 `dropped_iterations`와 latency만 계속 나빠짐** — 요청이 실패하는 게 아니라 queue에 쌓여서 느려지기만 하는 방식으로 우아하게 저하됨.

**MySQL/Redis는 전 구간에서 병목이 아니었다**(피크 내내 1.3 core 이하, RATE 3000까지도 0.49 core) — 순수 처리량의 상한은 전적으로 **backend CPU 2 vCPU 캡**에서 나온다.

**참고 수치**: SSE_VUS=300 켰을 때(RATE=130 기준) backend CPU가 1.996/2 core였던 것과 비교하면, **SSE 브로드캐스트 하나가 이 backend CPU 캡의 대부분(RATE=130에서 필요한 순수 bid 처리 비용 0.29 core를 빼면 약 1.7 core 상당)을 잡아먹고 있다**는 뜻 — "SSE와 bid 처리 사이 CPU 밸런싱"이 왜 필요한지에 대한 가장 직접적인 정량적 근거.

**핵심 발견 1 — 세마포어는 "총 일감"이 아니라 "동시 처리 개수"만 줄인다**: `SSE_VUS=300`이 고정이고 경매 3개 전부 `maxAuctionSseSubscriptions(16)` 이하라 VU 전원이 3개 다 구독한다 — 즉 이벤트 하나당 fan-out 대상(최대 300명)은 캡과 무관하게 동일하다. 제출률도 13,105~15,067/s로 캡 값과 상관없이 거의 일정 — **총 처리해야 할 브로드캐스트 일감 자체는 안 줄어든다.** 그 결과 **backend CPU도 캡과 무관하게 1.82~1.98/2 core로 거의 그대로**다. "세마포어로 CPU를 SSE에서 bid 쪽으로 돌려준다"는 원래 가설은 이 조건에서는 뚜렷하게 확인되지 않았다.

**핵심 발견 2 — 캡이 낮을수록 개별 task는 확실히 빨라짐**: 평균 task 소요시간이 1.90ms(cap=0) → 1.48 → 0.67 → 0.39 → 0.28 → 0.11ms(cap=10)로 거의 선형으로 감소. 메커니즘: 가상스레드는 이 컨테이너의 소수 carrier 스레드(2 vCPU에 대응) 위에서 돌아가는데, cap=0이면 수백 개가 동시에 carrier를 두고 경쟁해서 스케줄링 오버헤드·공유자원 경합이 커진다. 캡을 걸면 동시 경쟁하는 가상스레드 수 자체가 줄어서, 일단 실행되기 시작한 task는 더 빨리 끝난다. 다만 **총 CPU 사용량 감소로는 이어지지 않았음**(발견 1) — "적게·빠르게"와 "많이·느리게"가 총량에서 상쇄되는 것으로 보인다. 실제 유저 체감 지표인 `auction_sse_delivery_latency`도 캡을 낮춘다고 뚜렷이 개선되지 않았다(이상치 제외 시 9~46ms 범위에서 캡과 무관하게 오르내림) — 개별 전송은 빨라져도 300명 전원한테 다 나가는 총 시간은 안 줄어들 수 있다는 뜻.

**이상치 — cap=100의 delivery p95=2028ms**: 그 실행의 task 자체는 오히려 빨랐고(0.67ms) 제출률도 정상이라, 세마포어 문제가 아니라 **그 실행에만 낀 일시적 스톨**로 보임(팀에서 별도로 보고된 "Redis 세션 로그인 이슈"와 같은 계열일 가능성 — 세션이 Redis 기반으로 바뀐 뒤 나타난 현상). 재현되는지 cap=100만 재검증 필요.

**동작 메커니즘 상세** (대화 중 정리):
- `VirtualThreadSseTaskExecutor.execute()`의 `concurrencyLimiter.acquire()`는 **broadcast() 순회 가상스레드 하나**를 막는다 — emitter 300개가 각자 줄 서는 게 아니라, 이 순회자 하나가 `emitters.forEach` 루프 안에서 permit 없으면 멈췄다가 풀리면 다음 emitter로 넘어가는 구조.
- permit이 나면 `super.execute(...)`가 **그 emitter 전송 전용 새 가상스레드**를 만들어 실제 `emitter.send(...)`를 맡긴다 — `active` 게이지는 이 전송용 가상스레드들의 동시 실행 수.
- `acquire()` 블로킹은 JDK 19+에서 가상스레드 친화적이라(park 방식) carrier(진짜 OS/CPU) 스레드를 안 묶어두고 풀어준다.
- `AuctionStreamRedisSubscriber.onMessage()`가 `connectionManager.broadcast(...)`를 평범한 메서드 호출로 부르는 것만으로 비동기 실행되는 이유: `connectionManager`가 `@EnableAsync`로 등록된 프록시라, `@Async("auctionSseTaskExecutor")`를 가로채서 그 executor에 자동 제출한다(자기 자신 호출 self-invocation 함정과 달리, 여긴 다른 빈에서 주입받아 외부 호출이라 프록시를 정상적으로 거침). `onMessage()`는 제출만 해두고 곧바로 리턴 — 실제 브로드캐스트 부하는 안 짊어짐.

**결론**: 이 세마포어는 "SSE와 bid 사이 CPU 밸런싱 손잡이"라기보다는 **"무제한으로 두면 개별 전송이 지저분해지는(스케줄링 경합) 걸 막아주는 안전장치"**에 더 가깝다. 원래 목표(backend CPU를 bid 처리에 돌려주기)를 달성하려면, 총 일감 자체를 줄이는 다른 접근(이벤트 배칭, 구독자별 선택적 발송 최적화, 직렬화 비용 절감 등)이 더 유효할 것으로 보인다.

### "task당 효율 상승 = 더 많은 메시지 처리 가능"은 증명된 게 아님 (후속 논의)

캡이 낮을수록 평균 task 소요시간이 줄어드는 걸(1.90ms→0.11ms) "그만큼 더 많은 메시지를 처리할 잠재력이 생겼다"로 해석하고 싶어지는데, **이번 스윕 데이터로는 증명되지 않는다.** 이유:

- 제출률(13~15k/s)이 캡과 무관하게 거의 일정했다는 건, **executor가 이번 부하로는 한 번도 한계까지 안 밀렸다**는 뜻 — 여유 용량이 실제로 있었는지조차 시험이 안 됐다.
- 유저 체감 지표(`auction_sse_delivery_latency`)도 캡 낮다고 뚜렷이 개선 안 됨(이상치 제외 9~46ms 범위에서 캡과 무관하게 오르내림) — task의 CPU 시간이 줄어도 실제 배달 시간엔 네트워크 I/O 등 다른 요소가 더 크게 작용하는 것으로 보임.

**증명하려면 필요한 것**:
1. **진짜로 executor를 포화시키는 부하** — 지금보다 SSE_VUS를 훨씬 크게 올리거나, 경합을 줄여 낙찰률/이벤트 발생량 자체를 크게 늘려서 제출률이 처리 한계에 부딪히게 만들어야 함.
2. **"전체 배달 완료 시간" 지표 신설** — 지금은 emitter 1개당 전송 시간(task duration)만 있고, `broadcast()` 하나가 구독자 전원(예: 300명)에게 다 나가는 데 걸리는 총 시간을 재는 지표가 없음. `broadcast()` 메서드 전체를 감싸는 Timer를 추가해야 "캡을 낮추면 개별은 빠른데 전체 완료는 오히려 늦어지는지/빨라지는지"를 직접 비교 가능.
3. **가장 깔끔한 방법은 실부하테스트가 아니라 격리된 벤치마크**: `VirtualThreadSseTaskExecutor`만 떼어내서 고정 개수(예: 10,000개)의 동일한 CPU 작업을 캡 값별로 넣고 총 완료 시간을 재면, 네트워크 I/O·입찰 경합 같은 잡음 없이 "캡이 총 처리량에 미치는 순수 효과"만 볼 수 있음.

아직 실행 안 함 — 다음 스텝 후보로 남겨둠.

### broadcast() 순회와 emitter.send() 전송을 다른 executor로 분리하는 안 (후속 논의)

`broadcast()` 자체가 `@Async("auctionSseTaskExecutor")`라서, `onMessage()`가 `broadcast()`를 호출하는 순간 **같은 `auctionSseTaskExecutor`(같은 세마포어)에서 permit 하나를 요구**하고, 그 permit은 `broadcast()`가 emitter 전원을 순회하는 **루프 전체 기간 동안 붙잡혀 있다**(루프 안에서 emitter마다 또 별도로 permit을 하나씩 더 얻어야 함).

**문제**: 순회(coordination)는 가벼운 작업인데도 실제 전송(send)용 permit과 **같은 예산을 나눠 쓴다.** 경매 여러 개에서 이벤트가 거의 동시에 터지면, 각 `broadcast()`가 각자 permit을 하나씩 붙잡고 있어서 실제 전송에 쓸 수 있는 permit이 `(cap - 동시 진행 중인 broadcast 수)`로 줄어든다 — 조정 비용이 실제 작업 예산을 갉아먹는 구조.

**대안 비교**:
- **별도 세마포어(broadcast용/send용 executor 2개)**: 확실히 해결되지만, 캡을 2개 따로 튜닝해야 해서 설정 축이 늘어남.
- **broadcast()가 세마포어 없이 동작**: coordination이 send용 permit을 안 뺏게 되는 가장 깔끔한 방향. 다만 Redis pub/sub 리스너 스레드에서 완전히 동기로 돌리면, 300명 순회+dispatch 하는 동안 그 스레드가 묶여서 다음 Redis 메시지 수신이 밀릴 위험이 있음(리스너 스레드 풀이 작을수록 심함).

**결론(잠정)**: **"세마포어 있는 send 전용 executor" + "세마포어 없는 broadcast 전용 executor(가상스레드는 유지, 리스너 스레드는 안 묶임)"** 조합이 이 비효율을 없애면서 설정 복잡도도 최소로 늘어나는 방향으로 보임. 아직 구현/검증 안 함 — 다음 스텝 후보.

#### 캡이 꽉 찼을 때 broadcast() 호출자(caller) 스레드 자체가 막힘 — 프로필별 실제 영향

`broadcast()`가 `@Async`라서, `connectionManager.broadcast(event)`를 호출하는 코드 자체가 프록시를 거쳐 `VirtualThreadSseTaskExecutor.execute()`(캡이 꽉 차면 `acquire()`에서 블로킹)를 **동기적으로** 타게 된다 — 즉 **"호출자 스레드"가 캡이 꽉 찼을 때 그대로 멈춘다.** 이 호출자가 누구냐가 프로필별로 다르고, 둘 다 문제가 있다:

- **`redis` 프로필** (이번 스윕 대상): 호출자는 `AuctionStreamRedisSubscriber.onMessage()`를 부르는 스레드. `RedisPubSubConfig`가 `RedisMessageListenerContainer`에 `taskExecutor`를 따로 안 지정해서 Spring Data Redis 기본값(`SimpleAsyncTaskExecutor`, 메시지마다 새 **플랫폼 스레드** 생성)을 쓴다 — 서로 안 막히긴 하지만, 캡이 꽉 찬 상태가 지속되면 **블로킹된 플랫폼 스레드가 계속 쌓인다**(가상스레드와 달리 진짜 OS 자원을 씀 — 스택 메모리, 커널 스케줄링).
- **`local-sse` 프로필**: `LocalAuctionStreamPublisher.publish()`가 `connectionManager.broadcast(payload)`를 그냥 동기 호출하는데, 이 호출 경로가 **입찰 POST 요청을 처리하던 그 Tomcat 스레드 자체**(`AuctionCommandService.publishBidEvents()`)다. 캡이 꽉 차면 **입찰 처리 응답 스레드가 SSE permit을 기다리며 멈춘다** — 원래 목표(입찰 처리에 CPU 여유를 주기)와 정반대로, **캡을 걸수록 입찰 응답이 오히려 SSE 때문에 느려질 수 있는 구조**다.

이건 위 "broadcast()와 send를 분리하자"는 제안의 근거를 훨씬 강하게 만든다 — 단순히 "permit 예산을 나눠 쓴다" 수준이 아니라, **분리 안 하면 프로필에 따라 입찰 처리 스레드 자체가 SSE 캡에 막힐 수 있다**는 게 진짜 이유였다. (아직 구현/검증 안 함.)

# 후속 결론 — 위에서 남긴 다음 스텝 전부 해소됨 (#569/#495/#575/#579/#585, 2026-08-18)

위 섹션에서 미해결로 남겨뒀던 두 제안(broadcast/send executor 분리, 캡이 호출자 스레드를
막는 문제) 전부 실제로 구현·검증됐다. 순수 입찰 처리 없이 SSE fan-out만 격리해서 비교하는
전용 부하테스트(#569)로 이어져서, 이 파일(입찰+SSE가 섞인 조건)에서는 볼 수 없었던 신호들이
깨끗하게 드러났다. 상세 과정·k6 원본 데이터는
[`순수-SSE-fanout-부하테스트-569.md`](./순수-SSE-fanout-부하테스트-569.md)에, 최종 결론은
WEB-TEAM2-2gether 저장소의
[`495-sse-virtual-thread-fanout-conclusion.md`](495-sse-virtual-thread-fanout-conclusion.md)
(PR [#592](https://github.com/softeerbootcamp-8th/WEB-TEAM2-2gether/pull/592))에 정리했다.

**해소된 것들**:
1. **broadcast/send executor 분리** — `AuctionSseConnectionManager.broadcast()`(순수 조율,
   캡 없음) / `auctionSseTaskExecutor`(실제 send, 캡 있음)로 분리 완료(#507). 순회가 send
   포화 때문에 막히지 않는다.
2. **캡이 호출자 스레드를 막는 문제** — `concurrencyLimiter.acquire()`를 호출자가 아니라
   새로 띄운 가상스레드 안에서 하도록 옮김(#575). 다만 이게 "제출 즉시 가상스레드부터
   만들고 나서 permit을 기다리는" 새 문제(무제한 힙 누적 → OOM)를 낳아서, `tryAcquire()`
   기반 진짜 admission control(discard)로 다시 고침(#585).
3. **"세마포어가 CPU 밸런싱 손잡이"라는 원래 가설(#495)** — 이 파일(입찰+SSE 혼재 조건)의
   결론("총 일감은 안 줄어들어 CPU 밸런싱 효과 불명확")과 달리, **순수 SSE fan-out
   조건(#569)에서는 delay가 있고 부하가 서버 용량 이내면 가상스레드가 threadpool보다
   30~128배 빠르다**는 게 명확히 확인됨. 다만 그 전제(안정 구간, 서버 용량 이내)를 벗어나면
   threadpool이 낫거나(순수 CPU-bound) 가상스레드가 힙 OOM으로 죽는(과부하) 등 조건부라는
   것도 같이 확인됨 — "무조건 낫다/무조건 밸런싱 된다"는 아니었다.
4. **task당 효율 상승이 총 처리량 증가로 이어지는지(#419줄 논의)** — 순수 SSE fan-out
   조건에서 직접 확인됨: 캡을 걸어도(discard 방식) 가상스레드가 threadpool보다 총 배달량이
   더 많았다(구독자 1,000명 조건, 11,400/s vs 4,711/s) — 다만 그 대가로 일부 이벤트를
   조용히 유실한다는 트레이드오프가 있다.

이 파일(입찰 처리+SSE 혼재)은 여기서 마무리 — 이후 SSE 관련 실험은 전부 위 링크의 전용
문서에서 이어감.
