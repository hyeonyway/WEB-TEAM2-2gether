# ShedLock 기반 00:10 일일 통계 배치 적용 계획

관련 이슈: #307

## 목표

서울 시간 매일 00:10에 실행되는 `DailyStatisticScheduler`의 전날 통계 집계를
다중 애플리케이션 인스턴스에서도 한 번만 실행한다. 집계 대상 날짜와 기존 캐치업
규칙은 바꾸지 않는다.

## 현재 상태

- `@Scheduled(cron = "0 10 0 * * *", zone = "Asia/Seoul")`로 스케줄이 설정돼 있다.
- 서버 기동 시 마지막 시장 통계 다음 날부터 전날까지를 순서대로 보충한다.
- 일간 통계 upsert가 중복 행을 막지만, 여러 인스턴스가 동시에 집계하면 불필요한
  DB 부하와 갱신 경합이 발생할 수 있다.
- 분산 락 의존성, `LockProvider`, `shedlock` 테이블은 아직 없다.

## 구현 계획

1. `backend/build.gradle`에 ShedLock Spring/JDBC provider 의존성을 추가한다.
2. `@EnableSchedulerLock`과 MySQL `DataSource` 기반 `JdbcTemplateLockProvider`를 구성한다.
   시간 기준은 DB 시간 또는 애플리케이션 UTC 기준 중 현재 DB 설정과 일관된 방식을
   선택해 명시한다.
3. `shedlock` 테이블을 생성하는 DDL 또는 Flyway 마이그레이션을 추가한다.
   표준 컬럼은 `name`, `lock_until`, `locked_at`, `locked_by`로 유지한다.
4. `aggregateOnSchedule()`에 전용 락 이름(예: `daily-statistic-aggregation`)을 부여한다.
   `lockAtLeastFor`는 중복 트리거 방지에 필요한 최소 시간, `lockAtMostFor`는 가장 긴
   캐치업 집계 시간을 넘는 복구 한계로 설정한다.
5. 서버 기동 캐치업은 운영 요구에 따라 별도 락을 적용한다. 권장안은 정기 실행과
   같은 락으로 보호해, 기동 직후 00:10 실행과 겹쳐도 한 경로만 집계되도록 하는 것이다.
6. 락을 얻지 못한 인스턴스는 작업을 건너뛰며, 다음 스케줄 또는 재기동에서
   `market_daily_statistics` 기준으로 안전하게 재시도한다.

## 검증 계획

- 스케줄 크론과 `Asia/Seoul` 존이 유지되는지 확인한다.
- 락을 보유한 인스턴스가 있는 경우 두 번째 실행이 집계를 호출하지 않는지 검증한다.
- 락 만료 뒤에는 다음 실행이 정상적으로 재시도되는지 검증한다.
- 기동 캐치업과 정기 실행이 동시에 시작해도 동일 날짜의 집계가 한 번만 수행되는지
  MySQL 통합 테스트 또는 다중 애플리케이션 인스턴스 시나리오로 확인한다.
- `./gradlew test` 및 기존 MySQL 통계 통합 테스트를 실행한다.

## 결정이 필요한 값

| 항목 | 제안 | 결정 기준 |
| --- | --- | --- |
| 락 적용 범위 | 정기 실행 + 기동 캐치업 | 두 경로의 동시 집계 방지 |
| `lockAtLeastFor` | 1분 | 중복 실행만 억제하고 실패 복구 지연 최소화 |
| `lockAtMostFor` | 30분에서 시작 | 운영 데이터의 최장 캐치업 시간을 측정해 조정 |
| 시간 출처 | DB 시간 우선 검토 | 서버·DB 시계 불일치 방지 |

> 이 문서는 구현 전 합의와 리뷰 범위를 고정하기 위한 계획이다. 실제 설정값은
> 운영 DB 성능 및 인스턴스 구성 확인 후 구현 PR에서 확정한다.
