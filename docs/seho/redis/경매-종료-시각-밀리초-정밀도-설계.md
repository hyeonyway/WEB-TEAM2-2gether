# 이슈 #462 — Redis 경매 종료 projection 정밀도 설계

## 배경

Redis 종료 요청의 `occurredAt`과 DB 기준 `closeTime`은 모두 `Instant`지만, MySQL
`timestamp(6)`은 마이크로초까지만 저장한다. Redis 스케줄러의 경계는 정수 밀리초이며,
같은 밀리초 안에서 생성된 종료 요청은 DB 마감과 같은 종료 경계로 취급해야 한다.

실제 오류 사례에서 DB `closeTime`은 `10:52:08.632834`, Stream `occurredAt`은
`10:52:08.632101`이었다. 두 시각은 같은 `.632` 밀리초 경계지만, 기존 projection은 마이크로초까지
엄격하게 비교해 `아직 종료할 수 없는 경매입니다`로 거부했다.

## 결정

종료 projection의 마감 비교 전 양쪽 시각을 밀리초로 절삭한다.

```text
dbCloseTimeMillis = closeTime.truncatedTo(MILLIS)
eventOccurredAtMillis = occurredAt.truncatedTo(MILLIS)
dbCloseTimeMillis <= eventOccurredAtMillis 이면 종료 허용
```

Redis의 기존 마감 시각 및 ZSet score 생성 규칙은 바꾸지 않는다. 문제는 Redis 스케줄링이 아니라,
동일한 밀리초 경계의 Stream 이벤트를 DB projection이 마이크로초까지 비교해 거부한 데 있다.

## 보장과 트레이드오프

- 같은 밀리초에 속한 DB 마감 시각과 종료 요청은 동등한 종료 경계로 취급한다.
- 종료 요청은 실제 마감보다 최대 0.999ms 이를 수 있다. 이는 Redis의 밀리초 스케줄링 정밀도에서
  허용하는 경계 오차다.
- 이전 밀리초에 속한 종료 요청은 계속 거부한다.

## 검증

- DB `closeTime=...632834`와 Stream `occurredAt=...632101`처럼 같은 밀리초인 종료 요청은 처리한다.
- 서로 다른 밀리초인 조기 종료 요청은 거부한다.
