# Frontend 보호 화면 토스트 Auth Gate 설계

## 구현 상태

구현 완료. Header의 판매 등록·나의 대시보드·마이페이지는 공통 Auth gate를
사용하고, 비로그인 상태에서는 이동과 자동 로그인 모달 대신
`로그인이 필요합니다` 토스트를 표시한다. `/sell`, `/dashboard`, `/mypage`
직접 접근은 인증 초기화가 끝날 때까지 보호 화면을 숨기고, 익명 상태가 확정되면
토스트를 한 번 표시한 뒤 홈으로 `replace` 이동한다.

Toast는 외부 snapshot 저장소에 먼저 기록하므로 App 최초 렌더에서
`ToastContainer` 구독보다 보호 Route 차단이 먼저 실행돼도 안내가 유실되지
않는다. 인증 안내에는 중복 키를 적용해 활성 토스트가 있는 동안 연속 클릭으로
같은 안내가 쌓이지 않게 했다.

## 배경

현재 비로그인 접근 처리가 화면마다 다르다.

- 알림 버튼은 `로그인이 필요합니다` 토스트를 표시하고 현재 화면을 유지한다.
- 마이페이지 메뉴와 `/mypage` 직접 접근은 로그인 모달을 자동으로 연다.
- 판매 등록(`/sell`)과 나의 대시보드(`/dashboard`)는 비로그인 상태에서도
  화면에 접근할 수 있다.

로그인이 필요한 화면과 동작에 동일한 정책을 적용해 사용자가 접근 위치에 따라
서로 다른 안내를 받지 않도록 한다.

## 목표

- 판매 등록, 나의 대시보드, 마이페이지를 로그인 사용자만 볼 수 있게 한다.
- 비로그인 안내를 `로그인이 필요합니다` 토스트로 통일한다.
- 메뉴 클릭은 현재 화면을 유지하고, 직접 URL 접근은 보호 화면을 렌더링하지
  않은 채 홈으로 이동한다.
- 로그인 모달은 Header의 로그인 버튼으로만 연다.
- 인증 상태 확인이 끝나기 전에 보호 화면이나 비로그인 토스트를 노출하지 않는다.

## 범위

### 포함

- Header의 판매 등록, 나의 대시보드, 마이페이지 메뉴
- `/sell`, `/dashboard`, `/mypage` Route
- 알림 버튼과 공통으로 사용하는 비로그인 안내 문구
- 공통 Auth gate와 보호 Route 테스트

### 제외

- 홈, 카드 시세, 카드 경매 목록·상세 등 공개 화면
- 입찰, 찜 등 각 화면 내부의 개별 보호 동작
- 로그인 성공 뒤 차단됐던 목적지로 자동 이동하는 기능
- `<a href>`를 React Router 기반 SPA 이동으로 교체하는 작업
- 판매 등록, 대시보드, 알림의 도메인 API나 화면 비즈니스 로직 변경

전체 SPA 내부 이동 통일은 별도 GitHub 이슈 #112에서 처리한다.

## 접근 정책

| 진입 방식 | `initializing` | `anonymous` | `authenticated` |
|---|---|---|---|
| Header 보호 메뉴 클릭 | 이동 보류, 토스트 없음 | 이동 취소, 토스트 한 번 | 기존 목적지로 이동 |
| 보호 URL 직접 접근·새로고침 | 보호 화면 숨김 | 토스트 한 번, 홈으로 대체 이동 | 보호 화면 표시 |
| 알림 버튼 클릭 | 알림 UI를 열지 않음 | 토스트 한 번 | 알림 UI 표시 |
| Header 로그인 버튼 클릭 | 기존 동작 유지 | 로그인 모달 표시 | 기존 로그인 상태 UI 유지 |

보호 메뉴는 판매 등록, 나의 대시보드, 마이페이지다. 토스트 문구는
`로그인이 필요합니다` 하나를 사용한다.

## 설계 선택

### 채택: 공통 보호 Route와 메뉴 진입 함수

`RequireAuth`는 URL로 렌더링되는 보호 화면을 담당하고, Header 메뉴는 공통
Auth gate의 클릭 진입 함수를 사용한다. 두 경로는 같은 인증 상태와 토스트
문구를 사용하되, 차단 이후의 이동 정책만 다르게 둔다.

- Route 차단: 홈으로 `replace` 이동한다.
- 메뉴 차단: 브라우저 기본 이동을 취소하고 현재 화면을 유지한다.

화면별 `if` 문으로 각각 처리하는 방식은 토스트 문구와 인증 상태 판단이 다시
달라질 가능성이 커서 사용하지 않는다. Router 전역 메타데이터로 보호 여부를
관리하는 방식은 보호 Route가 세 개인 현재 규모에 비해 변경 범위가 크므로
도입하지 않는다.

## 컴포넌트 책임

### `RequireAuth`

- `authenticated`일 때만 `children`을 렌더링한다.
- `initializing` 동안 기존 인증 확인 UI를 표시하고 아무 이동도 하지 않는다.
- `anonymous`가 되면 토스트를 한 번 표시하고 홈으로 `replace` 이동한다.
- 로그인 모달과 로그인 성공 후 목적지 복귀 상태를 소유하지 않는다.

React Strict Mode나 effect 재실행으로 같은 차단에서 토스트가 중복되지 않도록
현재 접근에 대한 표시 여부를 ref 또는 동등한 일회성 상태로 관리한다.

### Toast 전달

직접 URL 접근은 앱 최초 렌더 직후 차단될 수 있다. 현재 `showToast()`는 브라우저
이벤트를 즉시 발행하므로 `ToastContainer`가 아직 이벤트를 구독하지 않았다면
안내가 사라질 수 있다.

인증 필요 토스트는 컨테이너의 mount 순서에 의존하지 않도록 한다. 토스트 목록을
외부 저장소에 먼저 기록한 뒤 구독자가 snapshot을 읽는 방식이나, 홈 이동 state를
전역 토스트 처리기가 소비하는 동등한 방식을 사용할 수 있다. 어느 방식을 택해도
다음 조건을 만족해야 한다.

- 최초 `/sell`, `/dashboard`, `/mypage` 접근에서도 토스트가 보인다.
- 소비한 이동 state나 토스트 항목은 제거해 새로고침과 재렌더링으로 반복되지
  않는다.
- 기존 Wallet 거래와 알림 토스트 동작은 유지된다.

### Header 보호 메뉴

판매 등록, 나의 대시보드, 마이페이지에 `requiresAuth` 메타데이터를 둔다.
공통 클릭 핸들러는 다음 순서로 동작한다.

```text
메뉴 클릭
→ 공개 메뉴면 기존 이동
→ 인증 완료 사용자면 기존 이동
→ 인증 확인 중이거나 비로그인 상태면 preventDefault()
→ 비로그인 상태일 때만 로그인 필요 토스트 표시
```

인증 확인 중 클릭은 잘못된 익명 판정을 피하기 위해 이동만 보류한다. 상태 확인
후 자동 이동하거나 로그인 모달을 열지는 않는다. 사용자가 결과를 확인한 뒤 다시
메뉴를 누르게 한다.

### 알림 버튼

기존 비로그인 토스트 동작을 유지한다. 공통 문구 상수나 공통 함수가 생기면 이를
사용해 Header 보호 메뉴와 메시지가 어긋나지 않게 한다. 알림 drawer와 API 호출
로직은 변경하지 않는다.

### Router

`/sell`, `/dashboard`, `/mypage`의 Route element를 모두 `RequireAuth`로
감싼다. 판매 등록 화면이 자체 Header를 받는 현재 구조는 그대로 유지하며,
인증에 성공한 경우의 렌더링 결과를 바꾸지 않는다.

## 동작 흐름

### 비로그인 메뉴 클릭

```text
Header 보호 메뉴 클릭
→ AuthStatus 확인
→ 기본 링크 이동 취소
→ "로그인이 필요합니다" 토스트
→ 현재 화면 유지
```

### 비로그인 직접 접근

```text
/sell, /dashboard, /mypage 진입
→ AuthStatus=initializing 동안 보호 화면 숨김
→ Refresh 결과가 anonymous
→ "로그인이 필요합니다" 토스트 한 번
→ navigate('/', {replace: true})
→ 브라우저 뒤로가기로 차단 URL에 즉시 재진입하지 않음
```

### 로그인 사용자 접근

```text
보호 메뉴 클릭 또는 보호 URL 진입
→ AuthStatus=authenticated
→ 기존 화면과 기능을 그대로 렌더링
```

## 오류와 경계 조건

- Refresh가 401이면 정상적인 `anonymous`로 보고 보호 접근을 차단한다.
- Refresh가 네트워크 또는 5xx로 실패하면 `AuthProvider`의 기존 복구 오류 안내를
  유지하고 다시 시도 버튼을 제공한다.
- `AuthStatus`는 `initializing | authenticated | anonymous`의 세 상태를
  유지한다. 이번 이슈에서는 별도 `error` 상태를 추가하지 않으며, 네트워크·5xx
  복구 실패도 권한 판정에서는 `anonymous`로 fail-closed 처리한다.
- 네트워크·5xx 뒤 보호 URL에 접근 중이었다면 `RequireAuth`는 보호 화면을
  노출하지 않고 로그인 필요 토스트를 표시한 뒤 홈으로 `replace` 이동한다.
  사용자가 복구 안내의 다시 시도를 눌러 성공하면 홈에서 `authenticated`로
  전환되며, 차단됐던 경로로 자동 복귀하지 않는다.
- 홈으로 이동하는 동안 `RequireAuth`가 재렌더링돼도 같은 접근의 토스트를
  중복 표시하지 않는다.
- 앱 최초 렌더의 Route 차단 토스트가 `ToastContainer`의 구독 시점 때문에
  유실되지 않는다.
- Header 메뉴를 빠르게 여러 번 누른 경우 클릭 횟수만큼 토스트를 쌓지 않도록
  기존 Toast 정책을 확인하고, 필요하면 인증 안내에 한해 중복 억제를 적용한다.
- 인증 여부는 Access Token 원문이나 JWT payload를 직접 읽지 않고
  `AuthProvider`의 `AuthStatus`만 사용한다.

## 테스트

### Router

- `/sell`, `/dashboard`, `/mypage`는 초기화 중 보호 화면을 렌더링하지 않는다.
- Refresh 401 뒤 각 보호 URL은 홈으로 이동하고 토스트를 한 번 표시한다.
- `AuthProvider`의 네트워크·5xx 복구 실패 테스트는 오류 안내, `anonymous`
  상태와 사용자 재시도 성공을 검증한다. Router의 `anonymous` 보호 경로
  테스트는 이 상태에서 보호 화면 미노출, 토스트와 홈 `replace`를 검증한다.
- 앱 최초 진입에서도 전역 Toast 구독 시점과 관계없이 안내가 표시된다.
- 보호 URL 차단 이동은 history를 `replace`한다.
- 로그인 사용자는 세 보호 화면을 정상적으로 볼 수 있다.
- 공개 Route는 비로그인 상태에서도 기존 화면을 표시한다.

### Header

- 비로그인 사용자가 판매 등록, 나의 대시보드, 마이페이지를 누르면 현재 경로를
  유지하고 같은 토스트를 표시한다.
- 인증 확인 중 보호 메뉴를 누르면 이동하거나 토스트를 표시하지 않는다.
- 로그인 사용자의 보호 메뉴 이동은 차단하지 않는다.
- 공개 메뉴는 인증 상태와 무관하게 기존 동작을 유지한다.

### 알림

- 비로그인 사용자가 알림을 누르면 drawer나 API 요청 없이 같은 토스트를
  표시한다.
- 로그인 사용자의 알림 drawer 동작은 회귀하지 않는다.

- [x] 보호 메뉴 클릭과 알림 클릭은 모두 `로그인이 필요합니다` 토스트를 사용한다.
- [x] 보호 URL 직접 접근은 토스트 뒤 홈으로 이동한다.
- [x] 보호 접근 때문에 로그인 모달이 자동으로 열리지 않는다.
- [x] 로그인 버튼으로 여는 로그인·회원가입 모달 동작은 유지된다.
- [x] 다른 담당 도메인의 API와 화면 비즈니스 로직은 변경하지 않는다.
